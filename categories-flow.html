    Por qué este patrón se siente tan ordenado

    Cada pieza tiene una sola responsabilidad, así que cuando algo cambie sabrás exactamente dónde tocar.

    • Controlador delgadosolo orquesta (3 líneas). Imposible que "haga cálculos mal".
    • Servicioel único lugar con try/catch, logging y mapeo. Un problema de red se arregla aquí y en ningún otro lado.
    • BaseServiceel try/catch escrito una vez; los 30 métodos futuros lo heredan gratis.
    • ViewModel + mapperla vista recibe datos ya listos; solo pinta.
    • ServiceResultcontrato consistente; el que llama siempre sabe qué esperar.

    Qué estamos siguiendo

    Este flujo no es improvisado: combina patrones de diseño reconocidos, la disciplina de Clean Architecture y un conjunto de mejores prácticas. Aquí están, con su nombre formal y dónde vive cada uno.

    Patrones de diseño

    • Result Pattern · ServiceResult<T>Devuelve éxito / error + datos + mensaje en vez de lanzar excepciones o devolver el dato pelón.
    • Execute-Around · ExecuteAsyncRodea la lógica con un try/catch + logging comunes, escritos una sola vez.
    • Template Method · BaseServiceClase base abstracta que define el esqueleto; los hijos rellenan huecos (ServiceName).
    • Adapter / Mapper · MapToViewModelTraduce DTO → ViewModel en la frontera entre capas.
    • Typed Client / Proxy · RefitUna interfaz tipada (ICategoriesApi) genera las llamadas HTTP.
    • Dependency Injection · constructoresLas clases reciben sus dependencias, no las crean.
    • Repository + Mediator · lado APIRepositorios abstraen el acceso a datos; MediatR (CQRS) separa comandos de consultas.

    Clean Architecture

    • Regla de dependenciaLas flechas apuntan hacia adentro: Web/API → Application → Domain. Nunca al revés.
    • Separación por capasCada proyecto tiene una responsabilidad fija (Domain, Application, Infrastructure, API, SDK, Web).
    • Domain aisladoEl núcleo de negocio no sabe que existe HTTP, EF Core ni la UI. Es C# puro.
    • Frontera por HTTPEl Web habla con la API por HTTP (vía el SDK), no accede a la base de datos directo.

    Mejores prácticas

    • DRYEl try/catch vive una vez en BaseService; no se repite en cada método.
    • Responsabilidad única (SRP)Controlador orquesta · servicio maneja errores · vista pinta. Cada uno una cosa.
    • No filtrar detallesEl error técnico va al log; al usuario un mensaje limpio y centralizado.
    • ViewModel > ViewBagDatos tipados con validación en compilación, no dinámicos.
    • Fail-safeDistingue error de la API vs. del Web; la cancelación no es un error.
